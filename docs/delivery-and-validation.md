# 개발 순서와 검증 계획

제품 전체의 개발 순서와 검증 기준이다. 코드 수준 계획은 단계별 명세에서 구체화한다. 초기 범위는 [PRD](PRD.md), 상태 규칙은 [비즈니스 로직](BUSINESS-LOGIC.md)을 따른다.

초기 배포 기준은 사용자가 확인한 개인·비상업용 **Vercel Hobby + Supabase Free**다. 두 사용자의 실험과 무료 한도 측정을 먼저 진행하고 회사 업무용 확장은 후속 단계로 구분한다. 회사 환경·코드 관련 검증은 해당 환경을 실제로 사용할 때 적용한다.

## 단계별 명세 범위

구현 명세는 완료 기준을 독립적으로 검증할 수 있는 범위로 나눈다. 각 단계에 테스트·독립 리뷰 등 적용되는 검증을 포함하며 파일럿까지 검증을 미루지 않는다. 전체 단계 순서는 미리 유지하고, 상세 명세는 해당 단계 직전에 앞 단계 결과를 반영해 작성한다.

| 순서 | 명세 범위 | 단계 완료 기준 | 필요한 조건 |
|---|---|---|---|
| 1 | [로컬 AI 런타임 연결 검증](impl-spec/001-local-ai-runtime-spike.md) | 격리 protocol 테스트와 실제 runtime의 질문·이벤트·중단·저장 맥락 증거 | TypeScript/Node 실험. 실제 호출은 허용 계정·model·실효 권한 확인 후 수행 |
| 2 | [웹 기본 흐름](impl-spec/archive/002-web-base-experience.md) | 연결 선택·공동 대화·발신·개인 입력·정지·결과를 모의 runtime로 체험 | 실제 연동과 독립적인 Next.js/TypeScript 화면. 모의 결과는 연결 성공의 증거가 아님 |
| 2 다음 선행 검증 | [허용된 런타임 도구](impl-spec/archive/003-scoped-runtime-tools.md) | 실제 모델의 allowlisted 파일 읽기·구조화된 로컬 질문 callback·저장 thread 도구 보존 확인 완료 | 001에서 드러난 파일 도구 미확인을 해소한 합성 호환성 검사. 실제 공동 질문 왕복과 구분 |
| 3 | 공동 조사 | 두 binding 사이 질문·답변, 인증·기기 scope·내구 기록이 한 흐름으로 동작 | 로컬 Auth/Postgres/Realtime 통합과 실제 두 AI 계정·세션 경로. 원격 검증에는 클라우드 계정/프로젝트 필요 |
| 4 | 사용자 개입과 복구 | 개인 설명 격리·방향 변경·정지·재접속·UNKNOWN 복구 검증 | 앞 단계의 실행 상태·권한·저장 계약. 기본 중단/UNKNOWN은 1·3단계에도 포함 |
| 5 | 두 PC 파일럿·운영 준비 | 실제 환경·다른 업무 도메인·비용·채택 부담 확인 | 앞 단계 통합, 데이터 공유 허용, 배포·운영 조건 |

후속 행은 명세 작성 순서이며 전체 상세 계획을 미리 고정하지 않는다. 한 제품 단계에 별도로 검증할 작은 선행 명세를 추가할 수 있으므로 명세 번호와 단계 번호는 같을 필요가 없다. 기존 세션 L3나 다른 provider가 제품 성립에 필수이면 해당 호환성 실험을 실제 공동 조사 연동보다 먼저 추가한다. 화면 체험은 독립적으로 진행할 수 있지만 그 결과로 기존 앱 연결 가능성을 판정하지 않는다. 공통 메시지·상태·권한의 기준은 [BUSINESS-LOGIC](BUSINESS-LOGIC.md)에 유지하고 각 명세에서 중복 정의하지 않는다.

공동 조사의 사람 인증·방 접근과 기기 pairing/binding은 실제 통합·브라우저·독립 리뷰를 완료했다. [006](impl-spec/archive/006-durable-investigation-coordinator.md)의 내구 조정은 실제 DB·HTTP·가짜 driver 18개와 workflow browser 4건을 통과했고 독립 구현 리뷰 round1도 미해결 CRITICAL/HIGH 없이 통과했다. 현재 모델·계약·화면은 [DB-SCHEMA](DB-SCHEMA.md), [API-SPEC](API-SPEC.md), [FRONTEND-ARCHITECTURE](FRONTEND-ARCHITECTURE.md)가 설명한다. [007](impl-spec/007-owned-codex-workflow-runner.md)은 connector-owned Codex·local intent/저널/outbox·lease/control과 binding별 로컬 모델/effort 설정의 구현·검증 단계다. 실제 provider 왕복·기존 설정 유지·독립 구현 리뷰가 남아 있어 완료 보관하지 않는다. 다음 상세 범위는 웹 설정과 Claude이며, 기존 구독으로 공식 CLI에 직접 로그인하는 후보와 실제 Codex↔Claude 왕복을 별도로 확인한다. Realtime·개인 설명/전체 개입·두 PC는 이어 검증한다.

006 리뷰의 후속 성능 항목은 방 전체의 과거 workflow rows/receipt 잠금과 request의 room 인덱스 부재다. 현재는 두 사용자 초기 범위이며 확장성을 주장하지 않는다. 이력·lease receipt 증가에 따른 다른 방 지연을 측정한 뒤 현재 작업 rows 잠금과 room 기반 인덱스를 후속 migration에서 개선한다. 이미 적용한 SQL을 덮어쓰지 않는다.

## 0. 제품 성립 조건 실험

화면을 크게 만들기 전에 실제 팀 도구와 계정으로 아래를 확인한다.

| 실험 | 확인할 것 | 통과 근거 |
|---|---|---|
| 기존 맥락 연결 | 정확한 앱·버전의 L1/L2/L3 지원 | 보존·누락된 맥락, cwd, 기존 프로세스와의 관계 기록 |
| 관찰·입력·중단 | visible event, steer/queue, interrupt 종결 | 요청/적용/종료를 구분한 실행 trace |
| 두 PC 왕복 | 로컬 저장소 A/B, outbound 연결, 질문 하나 | 양쪽 코드 근거와 같은 식별자를 연결한 답변 |
| 비공개 설명 | 제품이 관리하는 별도 context·세션·권한 | 설명 transcript를 공동 owned 세션에 자동 import/resume/fork하지 않음; 기존 전역 선호·memory 보존과 구분 |
| 인증·과금 | 해당 제품 형태에 허용되는 공급자 인증 | 공식 조건·계정 적격성, 실제 호출 계정 확인 |
| 사내 환경 | 회사 프록시/VPN/절전·운영체제 | 실제 두 PC 접속과 단절·재연결 복구 |

여기서 L3가 안 되면 L1/L2의 전환 부담과 효과를 비교한다. 제품이 성립하려면 기존 세션 실시간 연결이 필수라는 판단이 나오면 해당 앱 연동부터 해결하고 화면 개발 범위를 확대하지 않는다.

현재 확보한 증거에는 Codex의 합성 새 실행·동일 thread/cwd의 저장 맥락 재개·실제 INTERRUPTED 종결과 제한 namespace의 실제 파일 읽기·로컬 질문 callback·저장 도구 재개가 포함된다. 질문 상대는 합성 fixture다. 위 두 PC·실제 상대 AI·개인 설명·제품 인증 조건은 아직 통과하지 않았다. 재현 범위와 남은 연결 실험은 [로컬 AI 연결 조사](local-ai-connection-research.md#이번에-실제-확인한-로컬-증거)에 기록한다.

## 1. 화면 체험용 prototype

공동 대화·AI 발신·개인 입력·중단 상태를 구현하고 모의 런타임으로 입력 의미를 검증한다. 실제 AI나 두 저장소와 연결했다고 표현하지 않는다. 회사 데이터 없이 사용한다.

수용: 두 개발자가 개인 설명/방향 수정/공동 발언을 구분하고, 정지 요청과 정지 완료를 구분할 수 있다. 화면 prototype의 통과는 실제 runtime·권한·복구 검증을 대체하지 않는다.

로컬 구현은 클라우드 계정 없이 시작할 수 있다. 선택한 Vercel/Supabase의 계정·프로젝트는 클라우드 수직 구현을 연결하기 전에 준비한다. 로컬 Supabase와 실제 AI 인증을 포함한 [단계별 준비 조건](onboarding-and-settings.md#개발-단계별-계정-준비)을 따른다.

## 2. 첫 실제 수직 구현

위 표의 3·4단계를 합친 통합 범위다. 3단계는 인증·기기 scope·질문 왕복·기본 중단/UNKNOWN을 검증하고, 4단계에서 개인 설명·방향 수정·재접속 복구까지 완성한다. 아래 수용 기준은 두 단계가 모두 통과한 뒤 확인한다.

- 제품은 별도 저장소로 만든다.
- 실제 사람 인증, 조사방 하나, 기기 두 개, 저장소 binding 두 개를 연결한다.
- 이미 실험한 Codex의 connector 소유 세션을 먼저 연동하고, 같은 계약의 Claude adapter와 참가자별 도구·모델·effort 선택을 추가한다. 같은 방의 Codex↔Claude 왕복, 각자의 설정 보존·지원 밖 조합 거절을 실제 검증한다. 각 adapter를 별도 단위로 확인하며 한 공급자의 성공을 다른 공급자의 완료 증거로 사용하지 않는다.
- durable 질문·답변·run과 Realtime 알림, 로컬 저널을 구현한다.
- 읽기·허용된 격리 테스트·수정 제안만 지원한다.
- 개인 설명 분리, 방향 수정, 자기 AI/방 전체 일시정지, UNKNOWN 복구를 포함한다.

수용: 실제 공동 문제 한 건을 두 PC에서 조사하고, 근거·수정 제안·담당자·양쪽 검증 시나리오를 남긴다.

## 3. 작은 파일럿

몇 건의 공동 조사 문제에서 현재 수동 중계 방식과 비교한다. 사례는 API 요청/응답 계약, 프런트엔드·백엔드 동작 차이, 공통 라이브러리 변경 영향, 버전 불일치, 환경 설정 등으로 나눈다. 서비스 간 통신 장애만을 제품의 사용 조건으로 두지 않는다.

초기 개인·비상업용 실험은 두 사용자가 공유 가능한 예제 저장소와 문제로 진행한다. 실제 사용량과 예상치의 차이를 확인하고 [무료 플랜 운영 기준](constraints-and-security.md#무료-플랜-운영-기준)의 전송 묶음·구독 수·저장량을 조정한다. 회사 코드와 문제를 사용하는 후속 파일럿은 해당 사용 범위·플랜·정책을 확인한 뒤 진행한다.

사용자가 든 수집기·관리자 백엔드의 판매 채널 경계는 첫 파일럿 후보로만 사용한다. 범용성을 확인하려면 다른 도메인의 저장소 조합과 다른 종류의 조사도 같은 방·연결·근거 흐름으로 수행한다. 제품 코어나 필수 설정에 판매·관리 전용 모델을 넣지 않는다. 실제 관리자 저장소의 구현은 파일럿에서 확인하며, 운영 채널에 실상품을 등록하거나 실제 판매 상태를 변경하는 검증은 기본 권한에 포함하지 않는다.

## 4. 운영 준비

조직 접근 검증, 기기 취소, 보관·삭제, 비용·한도, 모니터링, 버전 업데이트, 진단·복구 문서를 정리한다. 사내 사용을 승인받은 데이터 범위·공급자·환경에서 배포한다.

파일 수정·커밋·PR·배포 등 실행 확대는 별도 제품 요구로 다룬다. 실제 쓰기를 추가하면 작업 범위·승인·worktree·충돌·롤백과 필수 리뷰를 설계해야 한다.

## 의미 있는 필수 검증

테스트 이름은 기존 러너가 있으면 그 형식을 따르고 새 형식은 `should + behavior`를 사용한다. 아래는 구현할 테스트의 동작 기준이며 현재 작성되거나 통과한 테스트가 아니다.

| 검증 | 반드시 확인할 동작 |
|---|---|
| 질문 라우팅 | 지정 수신자만 실행; 일반 공동 발언으로 두 AI가 동시에 새 run을 시작하지 않음 |
| actor 위조 | AI body나 client role로 사람/관리자 권한을 얻지 못함 |
| 방 접근 | 다른 방·다른 조직·취소된 기기·비멤버의 읽기/쓰기 거절 |
| 로컬 scope | 웹의 임의 경로·remote shell 요청이 저장소 scope를 확대하지 못함 |
| session binding | 저장소와 cwd가 다른 session은 실행되지 않음; L0/L1/L2/L3 표시 정확 |
| 중복 요청 | 동일 idempotency key 재전달로 완료한 run이 자동 재실행되지 않음 |
| 호출 직후 crash | runtime 호출 후 기록 전 장애는 UNKNOWN; 자동 새 호출 없음 |
| lease takeover | 새 fence는 옛 결과 채택을 막되 옛 도구 종료를 보장했다고 표시하지 않음 |
| 동시 사용 | 같은 runtime session에 두 connector/앱이 active turn을 만들지 못함 |
| 방향 변경 | 이전 epoch의 늦은 결과가 현재 결론/후속 자동 입력으로 채택되지 않음 |
| 옛 질문 답변 | A 방향 변경 후 B 답변이 완료돼도 질문 origin epoch를 확인하고 A의 새 turn을 자동 시작하지 않음 |
| 중단 상태 | 요청·전달·runtime 종결 구분; interrupt 요청만으로 완료 표시하지 않음 |
| 중단/완료 경합 | interrupt 요청 중 자연 완료/실패를 실제 종결로 기록하고 결과 채택 여부는 별도 판정 |
| 개인 설명 이력 분리 | 제품의 설명 transcript·session ID·인계를 공동 세션에 자동 병합하지 않음; 전체 공급자 memory의 출처 격리로 확대하지 않음 |
| 재접속 | 구독 준비/DB 조회 사이 이벤트, 누락·중복·순서 역전 뒤 같은 이력 복원 |
| 오프라인 | 새 공동 run 시작 차단, 종결 미확인 표시, 로컬 결과 업로드 전 epoch 대조 |
| 코드 drift | branch/dirty 파일이 바뀌면 근거의 snapshot 차이를 보여주고 재검증 필요 표시 |
| 한도 | 공동 cycle의 반복 질문·시간/호출 한도에 사람 확인; 방향 변경·재접속·새 turn으로 카운터 초기화 안 됨; 금액 hard cap 가능 여부 구분 |
| delta 유실 | 미리보기 손실 후 확정 메시지를 정확히 복원 |
| 권한 취소 | 멤버/기기 취소 이후 요청과 Realtime/DB 접근이 실제 차단됨 |
| 첫 사용 | connector 없는 관찰, 준비 상태 안내, 저장소/session 확인, 중복 등록·권한 취소·지원 밖 도구 오류의 복구 경로 |
| 범용 조사 | 다른 도메인의 저장소 조합·조사 목표가 같은 협업 흐름을 사용하고, 판매·관리 전용 설정을 필수로 요구하지 않음 |
| 무료 플랜 | preview 묶음·client별 전달·heartbeat·조회까지 사용량 계산; 한도 접근 시 새 조사 차단과 확정 기록 유지; 휴면 안내·내보내기 복구 확인 |

## 테스트 계층

1. 프로토콜/state 전이 단위 테스트: revision, fencing, 실행 채택, 라우팅, 권한 판정.
2. 격리 integration: 실제 DB/RLS·알림 mock·가짜 runtime·저널 crash 지점으로 장애 검증.
3. 공급자 integration: 공식 runtime의 resume/interrupt/approval/event 기능 확인. 계정 과금·권한 범위를 명시한다.
4. browser E2E: 두 사용자·기기 시뮬레이션으로 공유/개인 화면, pause, reconnect 확인.
5. 실제 두 PC smoke: 회사 네트워크·기기 절전·재시작·앱 버전 차이 확인.

외부 판매 플랫폼이나 운영 데이터 변경을 정상 테스트의 의존성으로 넣지 않는다. 통과한 검사 입력과 코드가 같으면 재사용하고, 영향받은 부분이 바뀌었을 때만 다시 검증한다.

## 파일럿 가치 측정

| 지표 | 의미 |
|---|---|
| 사람 중계 시간 | AI 조사 결과를 이해·복사·다시 설명하는 실제 시간 |
| 첫 검증 가설까지 시간 | 그럴듯한 답변이 아닌 재현/코드 근거가 붙은 가설까지 시간 |
| 결론/해결까지 시간 | 조사와 실제 후속 수정·검증 시간을 구분 |
| 추가 질문·재조사 | 맥락 누락·잘못된 버전·가정 때문에 생긴 왕복 |
| 사람의 이해 | 원인·영향·수정 책임·남은 위험을 설명할 수 있는가 |
| 실패·비용 | UNKNOWN, 잘못된 공유·권한 요청, 재작업, 호출·전송·운영 비용 |
| 채택 부담 | 앱 전환·세션 이전·설치·기기 연결에 드는 시간 |

규모가 작은 파일럿의 수치를 일반적인 생산성 개선으로 확정하지 않는다. 문제 종류와 난이도를 함께 기록하고, 대화량 증가가 이해 부담을 키우는지도 평가한다.

## 구현 계획·승인 경계

이 문서는 제품 검토이며 코드 수준 구현계획은 첫 범위·도구·계정이 정해진 뒤 해당 제품의 `docs/impl-spec/`에 작성한다. 5개 이상 운영 파일 변경은 적용되는 AGENTS.md의 계획 승인 규칙을 따른다. 인증·권한·DB/API 구현에는 관련 테스트와 독립 reviewer가 필요하다.

현재까지 허용된 로컬 인증과 합성 저장소로 실제 Codex 호출을 수행했다. 공급자 계정 생성·유료 자원 구매·회사 코드의 외부 공유·제품 배포는 수행하지 않았다. 후속 구현에서는 이미 승인된 범위를 재사용하고 실제 미결 요구·명시적 경계만 확인한다.
